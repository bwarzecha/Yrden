# Tool System

Yrden's tool system lets LLMs call Swift functions during agent execution. Tools receive JSON arguments from the LLM, execute logic, and return results that feed back into the conversation.

The design prioritizes heterogeneous tool collections: all tool types (`TypedTool`, `MCPToolProxy`, `RetryingTool`, `ApprovalRequired`) conform to the base `Tool` protocol, which has zero associated types. This means you can store `[any Tool]` arrays without type erasure wrappers.

---

## Protocol Hierarchy

```
Tool                      <- base: JSON string -> AnyToolResult, zero associated types
  |-- TypedTool           <- adds Args + Output, auto-implements Tool.call()
  |-- MCPToolProxy        <- raw Tool (schema from MCP server)
  |-- MCPServerTool       <- raw Tool (direct MCP server connection)
  |-- RetryingTool<T>     <- wraps any Tool, retries on .failed
  |-- ApprovalRequired<T> <- overrides requiresApproval to true
```

---

## Tool (Base Protocol)

The foundation of the tool system. Zero associated types enable heterogeneous arrays.

```swift
public protocol Tool: Sendable {
    var name: String { get }
    var description: String { get }
    var definition: ToolDefinition { get }
    var requiresApproval: Bool { get }  // default: false
    func call(context: ToolContext, argumentsJSON: String) async throws -> AnyToolResult
}
```

- `name` -- Unique identifier matching `[a-zA-Z0-9_-]+`. The LLM uses this to invoke the tool.
- `description` -- Human-readable text shown to the LLM. The LLM uses this to decide when to call the tool.
- `definition` -- Full `ToolDefinition` including the JSON Schema for input parameters (sent to the LLM).
- `requiresApproval` -- When `true`, the agent pauses execution and returns a deferred result instead of running the tool. Defaults to `false`.
- `call(context:argumentsJSON:)` -- Executes the tool with raw JSON arguments and returns an erased result.

Any type conforming to `Tool` can be stored in `[any Tool]` alongside any other tool type.

## TypedTool Protocol

Adds compile-time type safety for arguments and output. This is the primary way to create custom tools.

```swift
public protocol TypedTool: Tool {
    associatedtype Args: SchemaType
    associatedtype Output: Sendable = String
    func execute(context: ToolContext, arguments: Args) async throws -> ToolResult<Output>
}
```

`TypedTool` provides default implementations for `definition` and `call()`:

- `definition` is derived automatically from `Args.jsonSchema` (generated by the `@Schema` macro).
- `call()` decodes the JSON string into `Args`, calls `execute()`, then erases the `Output` to `String` via `ToolResult.erased()`.

Swift infers `Args` and `Output` from the `execute()` signature, so you rarely need explicit typealiases.

### Creating a TypedTool

```swift
@Schema
struct SearchArgs {
    @Guide(description: "Natural language search query")
    let query: String

    @Guide(description: "Maximum results to return")
    let limit: Int
}

struct SearchTool: TypedTool {
    var name: String { "search" }
    var description: String { "Search the knowledge base" }

    func execute(
        context: ToolContext,
        arguments: SearchArgs
    ) async throws -> ToolResult<String> {
        let results = performSearch(arguments.query, limit: arguments.limit)
        return .success(results)
    }
}
```

The `@Schema` macro generates `SchemaType` conformance on `SearchArgs`, which produces the JSON Schema sent to the LLM. The `@Guide` macro adds descriptions to individual fields.

### Dependency Injection

Tools receive dependencies through constructor injection, not through `ToolContext`. The context carries framework metadata (run ID, step number, token usage); user dependencies belong on the tool itself.

```swift
struct DatabaseSearchTool: TypedTool {
    let database: DatabaseClient  // injected at construction time

    var name: String { "db_search" }
    var description: String { "Search the database" }

    func execute(
        context: ToolContext,
        arguments: SearchArgs
    ) async throws -> ToolResult<String> {
        let results = try await database.search(arguments.query)
        return .success(results.formatted())
    }
}

// Inject the dependency when creating the tool
let tool = DatabaseSearchTool(database: myDatabaseClient)
```

## ToolResult\<T\>

The return type from `TypedTool.execute()`. Represents three possible outcomes:

```swift
public enum ToolResult<T: Sendable>: Sendable {
    case success(T)
    case failure(Error)
    case deferred(DeferredToolCall)
}
```

| Case | Meaning |
|------|---------|
| `.success(T)` | Tool completed successfully with output |
| `.failure(Error)` | Tool failed; error message is sent to the LLM for potential retry |
| `.deferred(DeferredToolCall)` | Tool needs external resolution (human approval, async operation) |

### Convenience Initializers

```swift
// Text result (when Output == String)
ToolResult.text("Found 3 documents")        // .success("Found 3 documents")

// Error from a message string
ToolResult<String>.error("Database offline") // .failure(ToolExecutionError.custom("Database offline"))
```

### Type Erasure

`ToolResult<T>` is erased to `AnyToolResult` by the default `call()` implementation in `TypedTool`. The erasure converts `T` to `String` using these strategies in order:

1. If `T` is `String`, use directly.
2. If `T` is `JSONValue`, JSON-encode it.
3. If `T` conforms to `Encodable`, JSON-encode it.
4. Fall back to `String(describing:)`.

## AnyToolResult

The type-erased result used by the agent loop. This is what `Tool.call()` returns and what the `ToolExecutionEngine` processes.

```swift
public enum AnyToolResult: Sendable {
    case success(String)
    case denied(String)
    case replaced(String)
    case failed(Error)
    case deferred(DeferredToolCall)
}
```

| Case | Meaning | Sent to LLM as |
|------|---------|-----------------|
| `.success(String)` | Tool executed successfully | `ToolOutput.text(value)` |
| `.denied(String)` | Tool was denied by user | `ToolOutput.error("Tool denied: ...")` |
| `.replaced(String)` | Tool result was replaced with a synthetic value | `ToolOutput.text(value)` |
| `.failed(Error)` | Tool failed permanently | `ToolOutput.error("Tool failed: ...")` |
| `.deferred(DeferredToolCall)` | Tool is deferred pending external action | `ToolOutput.error("Tool deferred: ...")` |

Convert to `ToolOutput` (the wire format sent back to the LLM) with the `.toolOutput` property.

## ToolDefinition

The schema sent to the LLM describing an available tool.

```swift
public struct ToolDefinition: Codable, Sendable, Equatable, Hashable {
    public let name: String
    public let description: String
    public let inputSchema: JSONValue
}
```

For `TypedTool` conformers, this is generated automatically from `Args.jsonSchema`. For raw `Tool` conformers (like `MCPToolProxy`), you construct it manually.

```swift
let definition = ToolDefinition(
    name: "search",
    description: "Search the knowledge base",
    inputSchema: [
        "type": "object",
        "properties": [
            "query": ["type": "string", "description": "Search query"],
            "limit": ["type": "integer", "description": "Max results"]
        ],
        "required": ["query"]
    ]
)
```

## ToolCall

The LLM's request to invoke a tool. Parsed from the LLM response by the provider.

```swift
public struct ToolCall: Codable, Sendable, Equatable, Hashable {
    public let id: String
    public let name: String
    public let arguments: String  // always valid JSON
}
```

**Argument normalization**: Empty and whitespace-only argument strings are normalized to `"{}"` at construction time. This ensures downstream code can always assume valid JSON. The contract:

| Input | Normalized to |
|-------|---------------|
| `"{}"` | `"{}"` |
| `""` (empty) | `"{}"` |
| `"   "` (whitespace) | `"{}"` |
| Valid JSON | Unchanged |

---

## ToolOutput

The result sent back to the LLM after tool execution.

```swift
public enum ToolOutput: Codable, Sendable, Equatable, Hashable {
    case text(String)
    case json(JSONValue)
    case error(String)
}
```

- `.text` -- Plain text result (most common).
- `.json` -- Structured JSON result. Use the `.jsonString` property to get the encoded string.
- `.error` -- Error message the LLM can use to retry or explain the failure.

## ToolContext

Framework-provided metadata passed to every tool call. Contains execution state, not user dependencies.

```swift
public struct ToolContext: Sendable {
    public let model: any Model
    public let usage: Usage
    public let toolCallID: String?
    public let toolName: String?
    public let runStep: Int
    public let runID: String
    public let messages: [Message]
    public let retryAttempt: Int
}
```

| Property | Description |
|----------|-------------|
| `model` | The model being used for the current run |
| `usage` | Accumulated token usage so far |
| `toolCallID` | ID of the current tool call (nil outside tool execution) |
| `toolName` | Name of the tool being executed (nil outside tool execution) |
| `runStep` | Current step number in the agent run (increments each model call) |
| `runID` | Unique identifier for the agent run |
| `messages` | All messages in the conversation so far |
| `retryAttempt` | Current retry attempt (0 on first call, incremented by `RetryingTool`) |

## RetryingTool

Wraps any `Tool` and retries on failure. Useful for tools that call flaky external services.

```swift
let reliable = myTool.withRetries(3)
// or
let reliable = RetryingTool(myTool, maxRetries: 3)
```

Retry behavior:

| Result | Action |
|--------|--------|
| `.success` | Return immediately |
| `.denied` | Return immediately |
| `.replaced` | Return immediately |
| `.deferred` | Return immediately |
| `.failed` | Retry (up to `maxRetries`) |
| Thrown error | Retry (up to `maxRetries`) |
| `CancellationError` | Re-throw immediately (never retried) |

Total attempts = 1 (initial) + `maxRetries`. The `ToolContext.retryAttempt` field is set to the current attempt number (0-based) so tools can adjust behavior on retries.

If all attempts fail, returns `.failed` with the last error.

```swift
let agent = try Agent<String>(
    model: model,
    systemPrompt: "...",
    tools: [
        stableTool,
        flakyTool.withRetries(3)  // wraps in RetryingTool
    ]
)
```

## ApprovalRequired

Wraps any `Tool` and overrides `requiresApproval` to `true`. When the agent encounters a tool marked as requiring approval, it pauses execution and returns a deferred result instead of executing the tool.

```swift
let safeTool = dangerousTool.requireApproval()
// or
let safeTool = ApprovalRequired(dangerousTool)
```

The wrapper delegates all other properties and the `call()` method to the wrapped tool.

---

## DeferredToolCall

Represents a tool call that needs external resolution before it can proceed.

```swift
public struct DeferredToolCall: Sendable, Codable, Equatable, Hashable {
    public let id: String
    public let reason: String
    public let kind: DeferralKind
}

public enum DeferralKind: String, Sendable, Codable {
    case approval   // needs human approval
    case external   // needs external operation
    case custom     // application-defined
}
```

Convenience constructors:

```swift
DeferredToolCall.needsApproval(reason: "Shell command requires approval")
DeferredToolCall.external(reason: "Waiting for payment processor callback")
```

## ToolExecutionEngine

Handles the mechanics of executing tool calls with timeout support. The `Agent` delegates tool execution to this engine.

```swift
let engine = ToolExecutionEngine(tools: myTools, timeout: .seconds(30))

// Single tool
let result = try await engine.execute(call: toolCall, context: context)

// Batch execution
let batch = try await engine.executeAll(calls: toolCalls, baseContext: context)
```

### Timeout Behavior

When a timeout is configured, each tool call races against a timer. If the tool does not complete within the timeout, a `ToolTimeoutError` is thrown.

```swift
public struct ToolTimeoutError: Error, Sendable, Equatable {
    public let toolName: String
    public let timeout: Duration
}
```

### Batch Execution and Approval

When executing multiple tool calls, the engine first checks if any tool requires approval. If so, it returns deferred results for ALL approval-requiring tools without executing any tools. This ensures the LLM receives a `tool_result` for every `tool_use` it requested.

For non-approval deferrals during execution, the engine stops processing further calls after encountering the first deferral.

---

## ToolExecutionError

Errors that occur during tool execution.

```swift
public enum ToolExecutionError: Error, Sendable, Equatable {
    case custom(String)
    case argumentParsing(String)
    case argumentValidation(String)
    case toolNotFound(String)
}
```

| Case | When it occurs |
|------|----------------|
| `.custom(String)` | Application-defined error from `ToolResult.error("...")` |
| `.argumentParsing(String)` | JSON decoding of arguments failed (invalid JSON or type mismatch) |
| `.argumentValidation(String)` | Arguments decoded but failed validation constraints |
| `.toolNotFound(String)` | No tool with the given name was found in the tool array |

## MCP Tool Integration

MCP (Model Context Protocol) tools are exposed to the agent through two types that conform to the base `Tool` protocol.

### MCPToolProxy

Routes tool calls through an `MCPCoordinator`, which manages connection lifecycle, reconnection, and timeouts. This is the recommended approach for coordinator-managed MCP connections.

```swift
let proxy = MCPToolProxy(
    serverID: "filesystem",
    toolInfo: toolInfo,
    coordinator: coordinator
)

let agent = try Agent<String>(model: model, tools: [proxy])
```

The proxy never holds connection state directly. All calls are routed through the coordinator, ensuring transparent reconnection and consistent timeout handling.

### MCPServerTool

Calls an `MCPServerConnection` directly. Use this when working with a server connection outside of a coordinator.

```swift
// Created via MCPServerConnection.tools()
let tools = try await serverConnection.tools()
let agent = try Agent<String>(model: model, tools: tools)
```

### MCPToolError

MCP-specific errors:

```swift
public enum MCPToolError: Error, Sendable, Equatable {
    case toolReturnedError(name: String, message: String)
    case executionFailed(name: String, server: String, message: String)
    case serverDisconnected(serverID: String)
    case toolCancelled(serverID: String, tool: String)
}
```

## Built-in Tools

Yrden provides three built-in tools for file system and shell operations. All three share a `PathValidator` for consistent security boundaries.

### BuiltInTools Factory

Create all built-in tools with shared configuration:

```swift
let tools = try await BuiltInTools(
    workingDirectory: "/Users/alice/project",
    allowedWriteDirectories: ["/Users/alice/project"],
    deniedReadDirectories: ["~/.ssh", "~/.aws", "~/.gnupg"],
    shellApprovalRequired: true  // default
)

let agent = try Agent<String>(model: model, tools: tools.all)
```

The `all` property returns `[shell, readFile, writeFile]` as `[any Tool]`.

### ShellTool

Executes shell commands with the user's full environment (Homebrew, nvm, pyenv, etc.).

```swift
@Schema(description: "Execute a shell command")
struct ShellToolArgs {
    let command: String
    let workingDirectory: String?
    let timeout: Int?  // default: 120, max: 600
}
```

Features:
- **CWD tracking** -- Working directory persists between calls via a sentinel marker.
- **Output truncation** -- Output exceeding 30,000 characters is truncated with head+tail preservation (60% head, 40% tail). Full output is saved to a spillover file.
- **Timeout** -- Commands are terminated after the configured timeout (default 120 seconds, max 600 seconds).
- **Approval required** -- Shell commands require approval by default (`requiresApproval: true`).
- **Path validation** -- Working directory changes are validated against the `PathValidator`.

### ReadFileTool

Reads file contents with line numbers, offset/limit pagination, and truncation.

```swift
@Schema(description: "Read a file's contents with optional line range")
struct ReadFileArgs {
    let path: String
    let offset: Int?   // 1-based starting line
    let limit: Int?    // max lines to read (default: 500)
}
```

Three-layer defense against token waste:
1. **Line count limit** -- Default 500 lines per read.
2. **Per-line truncation** -- Lines longer than 4,000 characters are truncated.
3. **Total character cap** -- Output capped at 100,000 characters via `OutputTruncation`.

Also detects binary files (null bytes in first 8KB) and returns an error.

### WriteFileTool

Writes content to a file atomically with path validation.

```swift
@Schema(description: "Write content to a file, creating it if it doesn't exist")
struct WriteFileArgs {
    let path: String
    let content: String
}
```

Features:
- **Atomic writes** -- Prevents partial writes on failure.
- **Auto-creates parent directories** -- Creates intermediate directories if needed.
- **Size limit** -- Maximum 10 MB per write to prevent accidental large writes.
- **Path validation** -- Write path must be within allowed write directories.

### PathValidator

Validates file paths against allowed and denied directory lists. Used by all three built-in tools.

```swift
let validator = PathValidator(
    allowedReadDirectories: ["/"],           // read from anywhere (default)
    allowedWriteDirectories: ["/Users/alice/project"],
    deniedReadDirectories: ["~/.ssh", "~/.aws", "~/.gnupg"]
)
```

- Resolves paths to absolute, follows symlinks via `realpath(3)`.
- Normalizes macOS aliases (`/var` to `/private/var`).
- Denied directories take priority over allowed directories.
- Throws `PathValidationError` on violation.

## Heterogeneous Tool Arrays

All tool types conform to `Tool`, so they can be mixed freely in a single array:

```swift
let tools: [any Tool] = [
    SearchTool(),                          // TypedTool
    mcpProxy,                              // MCPToolProxy
    flakyExternalTool.withRetries(3),      // RetryingTool<FlakyExternalTool>
    shellTool.requireApproval(),           // ApprovalRequired<ShellTool>
]

let agent = try Agent<String>(
    model: model,
    systemPrompt: "You are a helpful assistant.",
    tools: tools
)
```

Wrappers compose naturally:

```swift
// Retry a flaky tool AND require approval
let tool = flakyTool
    .withRetries(3)
    .requireApproval()
// Type: ApprovalRequired<RetryingTool<FlakyTool>>
```

## Implementing a Raw Tool

If you need full control over JSON parsing (bypassing `TypedTool`'s automatic decoding), conform to `Tool` directly:

```swift
struct RawEchoTool: Tool {
    var name: String { "echo" }
    var description: String { "Echo back the raw JSON arguments" }

    var definition: ToolDefinition {
        ToolDefinition(
            name: name,
            description: description,
            inputSchema: [
                "type": "object",
                "properties": [
                    "message": ["type": "string"]
                ],
                "required": ["message"]
            ]
        )
    }

    func call(
        context: ToolContext,
        argumentsJSON: String
    ) async throws -> AnyToolResult {
        return .success("You said: \(argumentsJSON)")
    }
}
```

This is what `MCPToolProxy` and `MCPServerTool` do -- they receive schemas from MCP servers at runtime and cannot use compile-time type generation.

## Complete Example

Putting it all together with an agent:

```swift
import Yrden

// Define argument types with @Schema
@Schema
struct WeatherArgs {
    @Guide(description: "City name to get weather for")
    let city: String
}

@Schema
struct CalculatorArgs {
    @Guide(description: "Mathematical expression to evaluate")
    let expression: String
}

// Define tools
struct WeatherTool: TypedTool {
    let apiClient: WeatherAPIClient

    var name: String { "get_weather" }
    var description: String { "Get current weather for a city" }

    func execute(
        context: ToolContext,
        arguments: WeatherArgs
    ) async throws -> ToolResult<String> {
        let weather = try await apiClient.fetch(city: arguments.city)
        return .success("\(weather.temp)F, \(weather.condition)")
    }
}

struct CalculatorTool: TypedTool {
    var name: String { "calculate" }
    var description: String { "Evaluate a math expression" }

    func execute(
        context: ToolContext,
        arguments: CalculatorArgs
    ) async throws -> ToolResult<String> {
        guard let result = evaluate(arguments.expression) else {
            return .error("Invalid expression: \(arguments.expression)")
        }
        return .success(String(result))
    }
}

// Create agent with mixed tool types
let tools: [any Tool] = [
    WeatherTool(apiClient: weatherClient).withRetries(2),
    CalculatorTool(),
]

let agent = try Agent<String>(
    model: model,
    systemPrompt: "You are a helpful assistant with access to weather and calculator tools.",
    tools: tools
)

let run = try await agent.run("What's 72 minus the temperature in London?")
let answer = try run.result()
print(answer)
```
